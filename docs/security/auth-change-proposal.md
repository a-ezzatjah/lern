# تغییر پیشنهادی ورود و نشست — نیازمند تأیید

وضعیت جدید: مالک پیاده‌سازی و آزمون محلی را تأیید کرد و انجام شد. نتیجه نهایی و تفاوت‌های اجرایی در [auth-implementation.md](auth-implementation.md) است. اجرای migration روی دیتابیس فعلی/آنلاین هنوز انجام نشده است؛ این سند طرح اولیه را برای سابقه نگه می‌دارد.

هدف: بعد از خروج، تغییر رمز یا غیرفعال‌سازی، کوکی قدیمی دسترسی ندهد؛ پس از خطاهای پیاپی ورود، حساب موقتاً محدود شود. ورود با موبایل و رمز فعلی و حساب‌های موجود حفظ می‌شود.

| بخش | تغییر قابل بررسی | اثر بر داده/کاربر |
|---|---|---|
| نشست | جدول مستقل نشست با کلید تصادفی، UserId، ایجاد/آخرین فعالیت، انقضای قطعی و وضعیت ابطال؛ استفاده از ITicketStore استاندارد Cookie Authentication با ذخیره SQL | پس از عرضه این تغییر کاربران یک بار دوباره وارد می‌شوند؛ نشست در هر درخواست معتبرسنجی و هنگام خروج حذف/باطل می‌شود |
| تغییر رمز/نقش/غیرفعال‌سازی | ابطال همه نشست‌های کاربر در همان عملیات؛ ورود مجدد و مسیر خروج از همه دستگاه‌ها | دیگر دستگاه‌ها پس از تغییر رمز از حساب خارج می‌شوند؛ افزایش نقش نیازمند ورود مجدد است |
| قفل ورود | شمارنده و زمان پنجره خطا، LockoutUntil و سطح تأخیر در دیتابیس؛ به‌روزرسانی اتمی | ۵ خطا در ۱۵ دقیقه: قفل ۱۵ دقیقه؛ تکرار ۳۰ دقیقه، ۱ ساعت و افزایش تا سقف ۲۴ ساعت؛ پیام عمومی حفظ می‌شود |
| سقف حساب | محدودیت همزمان IP و شناسه نرمال‌شده؛ سقف IP فعلی نیز حفظ شود | تغییر IP شمارنده حساب را دور نمی‌زند؛ حمله قفل‌کردن حساب باید با بازیابی امن کنترل شود |
| عمر نشست | زمان بیکاری ۳۰ دقیقه و انقضای قطعی ۱۲ ساعت؛ remember-me مستقل با توکن هش‌شده حداکثر ۳۰ روز | برچسب «تا ۱۴ روز» فعلی باید با سیاست انتخاب‌شده هماهنگ شود؛ عملیات حساس نیازمند رمز تازه است |
| رمز | قالب نسخه‌دار با کتابخانه نگهداری‌شده؛ رمزهای PBKDF2 قدیمی با پارامتر فعلی بررسی و پس از ورود موفق ارتقا یابند | تغییر مستقیم Iterations فعلی ممنوع چون ورود همه کاربران قدیمی را خراب می‌کند؛ حداقل ۱۵ code point برای رمزهای جدید و فهرست رمزهای ضعیف/افشاشده |
| بازیابی/MFA | انتخاب ارائه‌دهنده و کانال تأیید مالک شماره؛ recovery یک‌بارمصرف/منقضی/هش‌شده و MFA مدیر | ایمیل فعلی اختیاری و تأییدنشده است؛ ارسال لینک reset به آن بدون تأیید مالکیت مجاز نیست؛ سرویس و هزینه باید مشخص شود |

آزمون پذیرش روی دیتابیس جدا با حساب‌های ساختگی: ورود با رمز قدیمی، ارتقای رمز، قفل و رفع قفل با زمان کنترل‌شده، همزمانی خطاها، خروج یک نشست و ابطال همه نشست‌ها، تغییر رمز/نقش/disable، زمان قطعی و بیکاری، جدایی دو کاربر، CSRF و عدم کش. اسرار و کوکی در خروجی تست چاپ نشوند.

migration باید ابتدا روی کپی ساختگی دیتابیس امتحان و script آن بازبینی شود. اجرا روی دیتابیس فعلی/میزبان، حذف داده و اتصال ارائه‌دهنده در این مرحله انجام نشده است.

مبنای توقف: فایل ارسالی [auth.md](auth.md) می‌گوید «Ask before changing an existing login flow that real users depend on.» و [hack.md](hack.md) می‌گوید «Ask me BEFORE risky changes: DB migrations, deleting data, auth rewrites…». تأیید این طرح، اجازه پیاده‌سازی و آزمون محلی است؛ مجوز اجرای migration روی محیط واقعی نیست.
