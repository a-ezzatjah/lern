# اصلاح ورود و نشست — ۲۰۲۶-۱۰-۱۱

تأیید مالک برای پیاده‌سازی محلی دریافت شد. کد و migration آماده‌اند؛ دیتابیس فعلی/آنلاین تغییر داده نشده و اجرای schema روی آن مرحله جداگانه است.

## آزمون و محدودیت

`dotnet run --project tools/AuthSecuritySmoke --no-launch-profile` برنامه تست مستقل با SQLite داخل حافظه، کاربر ساختگی و زمان کنترل‌شده است. startup فروشگاه یا تنظیم اتصال آن را نمی‌خواند؛ هیچ توکن/کوکی/هش واقعی در خروجی چاپ نمی‌شود. SQL Server مخصوص فروشگاه در این آزمون استفاده نشده؛ رفتار hintهای UPDLOCK/ROWLOCK و همزمانی چند replica باید پیش از انتشار روی دیتابیس آزمایشی SQL Server تأیید شود.

`dotnet run --project tools/SecuritySmoke --no-launch-profile` نیز محافظت CSRF، هدر، no-store و محدودیت IP را می‌سنجد. Secure کوکی با شبیه‌سازی TLS termination آزمایش می‌شود؛ آزمون TLS واقعی میزبان نیست. هیچ تستی MFA، reset یا email notification را تأیید نمی‌کند چون این قابلیت‌ها هنوز ساخته نشده‌اند.

نتیجه نهایی: ۷۰ بررسی AuthSecuritySmoke و ۳۷ بررسی SecuritySmoke موفق؛ مجموع ۱۰۷. build محلول و build ابزار AdminAccessSmoke موفق با صفر خطا. ابزار AdminAccessSmoke اجرا نشد. ممیزی NuGet چهار پروژه و پروژه تست، بسته آسیب‌پذیر شناخته‌شده گزارش نکرد؛ وابستگی SQLite تست به bundle نسخه 2.1.13 ارتقا یافت. EF ابزار طراحی نیز مدل را هم‌خوان با آخرین migration تشخیص داد. این‌ها نتیجه محیط محلی‌اند.

انتخاب رمز: PasswordHasher استاندارد و نگهداری‌شده ASP.NET Core با PBKDF2-HMAC-SHA512 و 600000 تکرار، salt تصادفی و قالب نسخه‌دار. Argon2id استفاده نشده؛ شرط ترجیح Argon2id/استفاده PBKDF2 فقط برای FIPS در S11 کیت عیناً محقق نیست. فهرست محلی کوچک نیز دیتاست جامع رمزهای افشاشده نیست. هیچ ادعای انطباق کامل کیت یا FIPS وجود ندارد.

## اعمال دیتابیس و انتشار

۱. وضعیت migration و backup/restore میزبان را بررسی کنید. اسکریپت [authentication-migration.sql](authentication-migration.sql) تنها delta پس از PrepareCheckoutShippingAndPayments است؛ دیتابیس باید migrationهای پیشین را داشته باشد. اجرای آن در این کار انجام نشده است.

۲. برای review آفلاین از factory طراحی استفاده شده؛ EF tools startup سایت را اجرا نمی‌کند و صرفاً مدل/SQL تولید می‌کند. migration افزودنی Users و جدول AuthenticationSessions است؛ داده حساب/سفارش حذف نمی‌شود.

۳. پس از تأیید صریح مالک، schema را روی دیتابیس مقصد اعمال و نسخه جدید سایت را اجرا کنید. تا پیش از اعمال schema، کد ورود جدید روی DB قدیمی کار نخواهد کرد. اجرای خودکار migration/seed هنگام startup به‌طور پیش‌فرض خاموش است؛ فقط تنظیم صریح Database:ApplyMigrationsOnStartup=true آن را فعال می‌کند و تمام migrationها و seedها را اجرا می‌کند؛ در production خاموش نگه دارید.

۴. کلیدهای DataProtection باید پایدار، با دسترسی محدود و برای چند replica مشترک باشند؛ از دست‌رفتن کلیدها نشست‌ها را نامعتبر می‌کند. SQL TLS با گواهی معتبر، backup، AllowedHosts و proxy مورد اعتماد را در میزبان تنظیم کنید.

۵. کاربران با کوکی‌های قبل از این تغییر یک بار دوباره وارد می‌شوند. rollback به binary قدیمی که قالب framework را نمی‌شناسد، ورود کاربران ارتقایافته را خراب می‌کند؛ rollback باید به نسخه سازگار با هر دو قالب باشد. Down migration جدول نشست و ستون‌های امنیتی را حذف می‌کند و بدون تأیید اجرا نشود.

هنوز باقی: MFA مدیر، بازیابی مالکیت شماره/ایمیل و اعلان قفل/تغییر رمز، blocklist جامع، پوشش SQL Server concurrent، آپلود امن کامل، CSP کامل، سیاست نگهداری داده و الزامات میزبان. برای انتشار عمومی صرف موفقیت این آزمون‌های محلی کافی نیست.
